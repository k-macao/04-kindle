# 同花顺行情面板（hithink-finance）

从同花顺官方 GitHub 仓库 [Hithink-Tech-Org/Financial-API](https://github.com/Hithink-Tech-Org/Financial-API)
的金融数据服务（hithink-finance）抓 A 股行情，排成四份产物：

| 产物 | 给谁看 | 刷新方式 |
| --- | --- | --- |
| `site/stocks.json` | 网页面板的全量清单 + 数据 | 工作流每 15 分钟重写（+ 体检补跑） |
| `site/stocks-manifest.json` | Kindle 多镜像新鲜度探测的小清单 | 与全量清单同轮生成，字段/指纹一致 |
| `site/stocks.html` | 浏览器卡片仪表盘 | 每 7 分钟拉一次 `stocks.json` |
| `site/stocks.epub` | Kindle 字模式卡片版（交给阅读器排版） | 每 7 分钟查一次清单，内容指纹变了才重下 |
| `site/stocks.txt` | Kindle 纯文本面板（EPUB 不可用时的回退） | 同上 |
| `site/stocks-leaders.json` | 每板块 A/H 同公司龙头的约 130 根完整日线 | 每轮随龙头/日线更新；Kindle 主清单不重复下载 |

面板是**结果优先的市场监视屏**，从上到下先给结论，再给行情明细：

| 段 | 内容 |
| --- | --- |
| **风险开关 / 板块机会池** | 进攻、中性、防守；纪律仓位上限；3 个持续/新进领先方向 + 2 个改善候选及失效条件 |
| **量价结果卡** | 市场状态、量价结论、真承接、派发预警、强弱结果、赚钱主线；首屏只放数据与信号 |
| **四工具结果卡** | 聪明钱命中、机构共识、半导体景气、算力与采用、组合收益、宏观覆盖 |
| **市场概览** | 全 A 5584 只的涨跌家数、涨跌停数、平均涨跌幅、两市成交额、涨幅前五/跌幅前五 |
| **指数 / 板块** | 13 个宽基 + 91 个同花顺行业指数；网页为密集小卡，Kindle 为两栏文字 |
| **A/H 龙头半年量价** | 91 个板块逐行核对；有 A/H 同公司成分股就动态选 1 只，显示 A/H 两边 26 周价量趋势；没有则明确写“暂无”，不硬凑 |
| **港股 / 涨停池** | 恒指、国指、恒科与 20 只龙头；涨停名称、时间、原因、连板数与封单额 |
| **板块轮动结果** | RRG 可用时补充四象限位置、今日迁移和领先信号；不替代当日量价结果 |

结果卡固定置顶，指数、91 个板块、港股与涨停明细往下排；RRG 有数据时作为额外轮动结果显示。
`volume_price` 无论 RRG 是否可用都生成，因此不会因为日 K 齐全就丢掉当日量价判断。

### 风险开关和板块机会池怎么读

风险开关先用当日市场宽度、涨跌停、宽基收盘位置与连板/封板质量得到情绪分，再用 RRG
里领先、改善、疲软、滞后的分布做中期校正（当前版本：当日情绪 70% + RRG 分布 30%）；
跌停显著多于涨停、多个板块出现派发信号时继续扣分。综合分 ≥65 为进攻、45–64 为中性、
<45 为防守。输出不是「预测明天涨跌」，而是先限制能承担的新风险：

| 状态 | 通用纪律仓位上限 | 面板动作 |
| --- | ---: | --- |
| 进攻 | 60%（情绪过热时主动降到 45%） | 可分批试仓，只参与最强方向 |
| 中性 | 30% | 只看最强方向，小仓等待确认 |
| 防守 | 10% | 不开新方向，只观察并管理已有风险 |
| 数据不足 | 0% | 等待完整市场宽度与情绪数据，所有方向仅观察 |

这些比例是**保守的通用纪律模板，不是个性化仓位建议或满仓目标**；面板同时固定提示单笔
风险模板 ≤0.5%。不知道账户规模、已有持仓和最大回撤承受力时，不输出更激进的仓位。

机会池按 RRG 象限、RS-Ratio/RS-Mom 横截面名次、最近轨迹持续性、象限迁移、当日强弱和
真承接/派发信号评分。最多列 5 个：优先保留 3 个持续或新进领先方向、2 个改善候选，避免
整张表只剩已经涨了很久的老主线。单日涨幅过大或出现长上影/高开低走会扣分并标「等待回落」
或「等待确认」；防守状态下全部强制标「仅观察」。每项都写失效条件。RRG 缺失时只能退到
单日抗跌榜，并明确标为低置信度、等待历史确认。板块指数本身不可直接成交，机会池是观察
顺序，不是买入指令。

### A/H 龙头半年量价怎么选

这里的 **A/H 龙头必须是同一家公司同时发行 A 股和 H 股**，不是随便拿一家 A 股和另一家
港股拼成一对。每周缓存 91 个行业板块的当前成分股，与 A/H 代码对及腾讯 A+H 实时榜单交叉
验证；旧代码、退市代码和 H 股已经没有行情的映射会被自动淘汰。对每个板块剩下的候选，按
**A 股最近 20 个交易日平均成交额**从高到低选 1 只。因此这里的“龙头”是可复算的流动性
龙头，不是永久不变的主观称号。

并非 91 个行业都有 A/H 同公司上市标的。没有符合条件的板块仍保留一行并明确写「暂无可验证
的 A/H 同公司成分股」；不会用普通 A 股代替，也不会跨行业硬凑。一个公司若同时属于多个同花顺
行业成分，可以在多个板块出现，但完整日线只存一份。

每只命中公司抓 A/H 两边约 130 根前复权日线（约半年），完整 OHLCV/成交额放在
`stocks-leaders.json`；`stocks.json`、网页和 Kindle 只带最近 26 周的聚合趋势及半年收益、
最大回撤、20 日平均成交额和「价升量增 / 价升量缩 / 价跌量增 / 价跌量缩」状态。这样网页能画
周收盘线＋周成交量柱，EPUB/TXT 也能用黑白字符看趋势，又不会让设备每 7 分钟重复拉几 MB 日线。

**不逐只列 5584 只个股**：明细只落在 `site/stocks.json`（`market` 是统计口径，
`indices` 是指数/板块明细）。Kindle 先看结果卡，再看行情表；板块轮动见 §6，
四工具字段见 [kindle-jrglobal.md](kindle-jrglobal.md)。

### 港股为什么走腾讯

同花顺的金融数据服务**只有 A 股**：实测请求港股行情返回 `code=1002`
（`Invalid parameter format`），港股域只公开了新股（IPO 打新）三个接口，没有行情。
所以港股改走**腾讯公开行情** `https://qt.gtimg.cn/q=hkHSI,hkHSCEI,...`（GBK，
`~` 分隔的纯文本），在 `tools/fetch_hk.py` 里解析。

两边**不混算延迟**：清单里 `index_timestamp` 是 A 股/板块的快照时间，
`hk.data_timestamp` 是港股行情时间，`data_timestamp` 取两者较大值（港股收盘
比 A 股晚一小时）。文本与网页上的港股段都会单独标「行情 <时间>」。

普通迷你走势图的数据来自历史 K 线接口（`/api/a-share/prices/historical-batch` 与
`/api/a-share-index/prices/historical-batch`，参数 `interval=1d`、`adjust=forward`，
每批 ≤10 个代码），只取最近 20 个交易日收盘价，存进清单的 `history` 字段
（`{thscode: [[毫秒时间, 收盘], ...]}`）。要改天数用 `fetch_stocks.py --history-days N`
（`0` = 不取历史，面板上就没有迷你图）。A/H 龙头另取约 130 根：A 股仍走同花顺批量接口，
H 股走腾讯 `hkfqkline` 前复权日线；两边都保留开高低收、成交量和可用时的成交额。

## 0. 先说清楚「一分钟」

- **服务端：盘中自循环，迟到则补收盘**。GitHub Actions 的 cron 在这个仓库**极不靠谱**
  （实测：配了每 15 分钟，4.2 小时内 0 次；11-24 的班次全部拖到 16:12 以后才开始）。
  `refresh-stocks.yml` 在抓取窗口内（北京 09:00–15:30，周一到周五）每 15 分钟一轮；
  若触发已迟到到窗口外，会比较 `stocks.json.data_time` 与最近应有工作日：缺快照就补抓一次，
  已有就立即退出。旧方案让窗口外 runner 空睡约 5.5 小时，反而把后续班次堵在队列里，最终
  面板停在前一交易日；现在不再跨夜占用 runner。盘中预算用完且还没收盘时，才用
  `workflow_dispatch` 交给下一棒。连续 4 轮抓取失败就中止且不交接。
  `refresh-stocks-watchdog.yml` 是额外保险：被叫醒时若盘中 `data_time` 落后 >25 分钟就补一枪。
- 判断「盘中」= 北京时间周一至周五 09:15–15:05；收盘后自循环自动停下，
  数据就停在收盘那一刻，这是正常的，面板会显示「已收盘」。

数据新鲜度以清单里的 `data_time`（快照数据时间）为准，不是生成时间；
收盘后快照时间不变，工作流按 `data_hash` 判断「行情没变就不提交」。同花顺快照信封的
`timestamp` 实际是**接口请求时间**：盘中可近似行情时刻，但收盘补抓不能照抄，否则前一日
收盘会被标成次日凌晨的「精确行情」。抓取器会把午休钳到 11:30、收盘后钳到 15:00、
开盘前/周末钳到上一工作日 15:00；港股仍使用腾讯逐条行情自带的 `quote_time`。

**面板自己会说实话**：纯文本/EPUB 抬头写「数据 2026-11-18 10:00:01 · 3 分钟前 ·
盘中」，网页版顶部徽章同步。但**「过期」只在「该有数据却没有」时才报**：

| 数据的时段 | 什么时候才算 STALE |
| --- | --- |
| 盘中 / 午休 | 超过 20 分钟没更新（这是真问题） |
| 已收盘 / 周末 | 超过 24 小时还没有新数据（跨过一个交易日） |
| 未开盘 | 同上 |

收盘后数据本来就不再变，所以凌晨或周末看面板会显示「已收盘（收盘后不再更新）」
而不是 STALE。早期版本是死比「现在 − 数据时间 > 20 分钟」，凌晨看必然报警，纯误报。
**午休（11:30–13:00）单列**：11:45 抓到的快照成交量跟 11:30 一样，标成「盘中」
会让人以为行情还在动。

看到 `未成交` / `--` 而不是 `0.00 手`，说明那一轮快照没有成交数据
（开盘前或接口抽风），不是成交为零。

**开盘前的空壳快照不会盖掉有效面板**：同花顺在开盘前会给「成交量全 0、个股没有
最新价」的快照（指数还带着前收盘点位）。`build_stocks.py` 会判定这种情况
（`empty_snapshot()`）：上一份面板有成交时直接报错退出、不写文件，工作流那一步
失败也就不会提交——设备继续显示上一份有成交的面板，等下一轮再更新。

## 1. API Key（GitHub 配置）

统一 API Key 在同花顺金融数据服务官网创建：<https://fuyao.aicubes.cn/admin/>。

放到仓库的 Actions Secret 里（**不要**写进代码、日志或 Git 提交）：

- Secret 名：**`THS_API_KEY`** 或 **`THS_KEY`**（官方名 `HITHINK_FINANCE_API_KEY` 也兼容）；
- 值：官网创建的统一 API Key。

工作流里已经接好了（`refresh-stocks.yml` 的「从同花顺抓一轮行情快照」步骤），
Key 缺失或接口报错时那一步直接失败、**不推送**，读者手上还是上一份面板。

本地跑时用环境变量（官方名优先，也兼容 `THS_API_KEY` / `THS_KEY` / `API_KEY`）：

```sh
export THS_API_KEY=…   # 或 THS_KEY=… / HITHINK_FINANCE_API_KEY=…
```

接口约定（见官方仓库 `docs/api/README.md`）：Base URL `https://fuyao.aicubes.cn`，
认证头 `X-api-key: <API_KEY>`，成功判断是 HTTP 200 **且**信封 `code == 0`。
这里只用五个接口：A 股快照、指数快照、涨停池、A 股历史 K 线、指数历史 K 线；
中文名用标的检索补，补过的缓存在 `site/stocks_names.json`。

## 2. 手动跑一轮（验证）

```sh
python tools/fetch_stocks.py --out stocks_data.json   # 抓取（含近 20 日 K 线）→ 中间产物（不进 Git）
python tools/build_stocks.py --data stocks_data.json --out site
python -m unittest discover -s tests                  # 含 tests/test_stocks.py
```

没 Key 时先看版式（演示数据，取自官方文档示例，面板上会标「演示数据」）：

```sh
python tools/build_stocks.py --demo --out site
python tools/build_stocks.py --demo-cross --out site   # 看「没有日 K」时的横截面版式
```

只看某几个指数/板块：`--indices 000001.SH`；不要涨停池：`--no-limit-up`；
不要板块轮动：`--no-rrg`；不要 A/H 龙头半年量价：`--no-ah-leaders`；
龙头日线根数：`--ah-history-days 130`；不要全市场概览（5584 只，最慢的一步）：
`--no-market`；不取普通港股段：`--no-hk`（A/H 龙头自己的 H 股验证与日线是独立子源）。

清单在 `tools/market_watchlist.py`：`INDICES`（13 宽基）、`SECTORS`（91 板块）、
`HK_INDICES`/`HK_STOCKS`（港股 3+20）。加一行 `(代码, 名字)` 即可，代码必须带后缀
（A 股 `000001.SH` / 板块 `881101.TI` / 港股 `hk00700`）。

**加代码前先确认它真的存在，名字也要对着目录抄**：同花顺对含非法代码的批量请求是**静默返回空**
（`code=0` 但 `item=[]`），不是报错——一个坏代码能让整批全丢，宽基指数曾经因此
13 个全灭。所以 `fetch_index_rows` 发现批次返回条数少于请求数，就逐个单取确认，
把真正坏的代码挑出来记进 `errors`，其余照常出面板。

板块判定也有坑：同花顺行业指数大多是 `881xxx/884xxx.TI`，但「有色金属」是
`000819.SH`——只按后缀判会把它排进【指数】段（宽基就变 14 个了），
所以先查清单里的板块代码集合，再退回后缀。

**现在的清单是拿目录逐条校对过的**（`catalog/ths-index-list?tag=industry`，
320 条，其中 881* 系列 90 个）。校对前那份清单里有 36 个板块的名字是错的
（代码对、名字错，比如 `881121.TI` 被写成「电力设备」，目录里是「半导体」），
盘面上等于挂错牌子——所以加代码时务必对着目录抄名字，别凭印象。

## 3. 本地实时（60 秒一轮）

```sh
HITHINK_FINANCE_API_KEY=… python tools/fetch_stocks.py --loop 60 --build
```

每 60 秒抓一轮并重排 `site/`，Ctrl+C 停止。适合开着电脑盯盘；Kindle/手机
打开 `site/stocks.html`（或部署后的 Pages 地址）就能看到每分钟的新数据。

## 4. Kindle 上看

插件新增 **Display mode → Stocks panel**，清单地址填 `site/stocks.json` 的
HTTPS 地址（和 EPUB/新闻一样，支持多地址与镜像自动切换）：

```
https://raw.githubusercontent.com/k-macao/04-kindle/main/site/stocks.json
```

每 7 分钟检查一次清单。配置仍可填 `stocks.json`，插件会自动改读同目录只有几 KB 的
`stocks-manifest.json`，短超时读取 raw、Pages、jsDelivr 等候选，解析后先比 `data_time`
（真实行情时间）、再比 `generated`，选择最新有效版本；不会再把「第一个 HTTP 200」当成最新，
也不会为了比 6 个镜像而重复下载 6 份全量行情。旧部署尚无小清单时，404 后兼容回退一次
`stocks.json`。线上候选比设备已接受缓存更旧时拒绝倒退并继续显示缓存。正文以 `data_hash`
为内容指纹，内容真的变化才重下 `stocks.epub`；只是重新发布时间变化不会白下同一本书。

新 EPUB 使用带序号文件名并从头打开。即使上一轮已写入新文件、但 KOReader 切换 ReaderUI 时
被打断，下一轮也会核对**实际打开路径**：屏幕仍是旧 `stocks-card` 时会再次切到目标文件，
而不是因为签名相同就只翻旧书。清旧文件时也会保护 ReaderUI 当前打开的那一本。
0.9.1 起，打开缓存 EPUB 导致 ReaderUI 重建后，新插件实例会立即接管并检查一次，再重新挂上
7 分钟定时器；`Last check` 与最后错误也会跨实例保存，不再误报 `never / No error`。
字体、行距、页边距继续跟着设备现有阅读设置走。

EPUB 里点屏幕打开的是 KOReader 阅读器菜单，不是纯文本面板的浮动菜单。因此
**工具 → 004 Report** 里固定提供 `Refresh now (starts if idle)`：即使 Status 显示
`Auto-start: off · now: idle`，也能一键启动并刷新；想重启后继续自动运行，再打开
`Auto-start on launch`。0.9.2 又移除了原先通过 `UIManager:show()` 放置的 0×0 后台窗口：
该窗口在部分 KOReader/Kindle 组合上仍会成为最上层并吞掉全屏触摸；现在只保留全局定时任务
与 ReaderUI 接力，不再放任何隐形触摸层。

EPUB 版是一串表格：市场概览 → 指数 → 板块（按涨跌幅，标「涨 N 跌 M」）→
港股 → 涨停池 → 板块轮动 RRG。crengine 不认 flex/grid/SVG，所以 Kindle 上**只有表格和标题**，
网页版的涨跌比例条、强度条、迷你走势图在 Kindle 上换成文字/表头说明。
纯文本版（`stocks.txt`）更省：板块两栏并排（中文按 2 列宽对齐），一屏能扫完。

清单里没有 `epub` 字段、或者 EPUB 下载失败（非 HTTPS / 不是 zip）时，
自动回退到纯文本 `stocks.txt`，不会白屏。刷新失败时页头明确显示 `OFFLINE / CACHED`，
提示同时带缓存的北京时间和年龄，不会把旧缓存伪装成已更新。状态菜单（Status）会显示行情的
`data_time`（超过 24 小时没更新标 `stale`）、已接受的 `generated`、实际清单来源、检查间隔
（`every 7m`）以及目标 STOCKS 文件；若 ReaderUI 仍开着旧卡片，会直接标
`OUTDATED EPUB STILL OPEN`。

## 5. 排错

- **工作流一跑就失败**：先看「从同花顺抓一轮行情快照」步骤的日志。
  `缺少同花顺 API Key` = Secret 没建或名字不对（必须是 `THS_API_KEY`、
  `THS_KEY` 或 `HITHINK_FINANCE_API_KEY`）；`code=2003` = Key 无效/无权限，去官网 Key 管理页重签；
  `code=4001` = 限流，脚本会自动退避重试 3 次。
- **面板是演示数据**：说明真实抓取还没跑成功过——`site/stocks.json` 里
  `"demo": true` 就是演示版，工作流跑通一轮会自动覆盖。
- **Kindle 上看到的是纯文本而不是卡片**：说明 EPUB 那条路没走通（清单里没有
  `epub`、地址不是 HTTPS、下载到的不是 zip）。插件会写一条
  `stocks epub failed, falling back to text` 到 `crash.log`，照着那条日志查。
- **Kindle 显示 OFFLINE / CACHED**：清单地址不通，用菜单里的
  `Check URLs (network)` 逐个试，换一条能通的地址（raw / Pages / jsDelivr）。
- **收盘后数据不变**：正常。快照时间停在收盘那一刻，`data_hash` 相同
  工作流就不提交；面板上看 `data_time` 就知道数据停在哪一刻。

## 6. 板块轮动 RRG / 横截面（策略来自 GitHub）

面板的量化分析段：91 个同花顺行业板块按 **RRG（相对旋转图）** 分到四个象限，回答
「今天这个板块是刚开始转强、还是强了很久在熄火」——单看涨跌幅排序看不出来。

### 策略出处

- 代码：GitHub [hugo2046/QuantsPlaybook](https://github.com/hugo2046/QuantsPlaybook)
  （约 6.9k ★，「量化研究 · 券商金工研报复现」）里的
  `C-择时类/相对旋转图RRG行业轮动/src/factor_algo.py`（JdK 比率法 RRG）；
- 信号：同目录 `src/strategy.py` 的 `select_by_quadrant`（信号 A：只留「领先」象限，
  按距中心 (100, 100) 的距离取前 N，**不补足**）；
- 研报：西部证券 2026-05-25《指数化配置系列研究（6）：相对旋转图 RRG 框架下的行业研究》。

那份实现依赖 pandas / numpy，本仓库的面板产物是纯文件，所以
`tools/sector_rrg.py` 把公式原样搬成标准库版（纯函数，无 I/O），
连 warm-up 行数都照它的《RRG 算法说明》核过：

```
RS       = close / benchmark × 100
RS-Ratio = MA_smooth(100 × RS_t / RS_{t-ratio})              中枢 100（X 轴）
RS-Mom   = MA_smooth(100 × RS-Ratio_t / RS-Ratio_{t-mom})    中枢 100（Y 轴）

象限 1 领先 (>100, >100) · 2 改善 (<100, >100)
     3 滞后 (<100, <100) · 4 疲软 (>100, <100)
```

- **基准**按研报 §2.1 口径取「板块等权组合净值」（各板块日收益等权复合、首日 1.0），
  不是某只宽基；RS-Ratio 只依赖基准的收益比，对基准绝对水平尺度不变。
- **参数**先试研报口径 `220/60/20`（要 319 根板块日 K，约一年半）；
  拿不够就退「短窗 `60/20/5`」（89 根），并在面板上写明用的是哪一套
  ——**不同参数不混着比**。两根都不够时这一段整段不出现，只在 `errors` 里留一句。
- **今日**：历史 K 线通常不含今天（盘中），所以用快照的最新价覆盖/补上今天那一行，
  盘中 15 分钟一轮就能看到点位在四个象限里挪动。

### 怎么读

| 现象 | 含义 |
| --- | --- |
| 落在**领先**且轨迹继续朝右上 | 相对强度在趋势上、动量还在抬——轮动的主线 |
| 从**改善**进入**领先** | 拐点确认（面板的「今日迁移」会点名） |
| 在**疲软**但今日仍在涨 | RS 还高、动量已跌破 100：强势在衰减，追高要留一半清醒 |
| 在**滞后**但今日反弹 | 超跌修复，不是趋势反转 |

网页版把四象限画成一张灰度图（横轴 RS-Ratio、纵轴 RS-Momentum，细线是最近 6 个
交易日的轨迹，黑点是信号 A 名单）；Kindle 的纯文本/EPUB 只有「象限计数 + 今日读数 +
四个象限的清单 + 表格」，crengine 不认 SVG。

### 开关与成本

```sh
python tools/fetch_stocks.py --out stocks_data.json            # 默认就算 RRG
python tools/fetch_stocks.py --no-rrg                          # 不算（省 10 次批量请求）
python tools/fetch_stocks.py --rrg-days 340 --rrg-top-n 6      # 日 K 根数 / 信号 A 的 N
python tools/fetch_stocks.py --rrg-preset short                # 锁死参数档（report / short）
python tools/fetch_stocks.py --rrg-cache-minutes 60            # 板块长期日 K 的缓存时长
```

91 个板块的 340 根日 K 是 10 次批量请求（每批 ≤10 个代码），比迷你走势图的 20 根重
得多；所以工作流那个「同一 runner 常驻循环」里，长期日 K 按「当天 + 60 分钟 + 同一
批代码」缓存，每轮只用快照最新价覆盖今天那一行。接口抽风时沿用当天早些时候的缓存
（面板的 `errors` 会写一句），不会让整段消失，更不会拖垮别的段。

### 没有板块日 K 时：自动退成「单日横截面」

RRG 的光滑与比率都要时间轴：研报口径要 319 根日 K，短窗也要 89 根。真实线上会遇到两种
情况——历史 K 线接口失败、或者只回了十几根；以前这一段会**整块消失**，面板最后空一块。
现在改成降级：

```
能算 RRG        → 【板块轮动 · RRG】四象限 + 信号 A
日 K 不够/取不到 → 【板块横截面】涨跌分布 + 量价 + 涨停题材 + 今日读数
```

两者**互斥**（同一位置只显示一个，`final_sections()` 统一裁决，RRG 优先），清单里也只会
留一个；`check()` 会查「清单里有 cross 但页面/文本没这一段」「两段同时存在」。

横截面这一段只用单日快照，所以只回答当天能证明的三件事——**不编造象限**：

| 读什么 | 怎么算 |
| --- | --- |
| 普涨/普跌还是轮动 | 91 个板块的红/绿/平、中位数、**离散度（总体标准差）**：九成翻绿且离散度 < 1.5 → 整体减仓式普跌；离散度 ≥ 2 → 真有钱在板块间切换 |
| 情绪面 | 全 A 涨停/跌停（跌停 ≥ 涨停 1.5 倍时点名「尾部比赚钱的尾部粗」） |
| 大盘 vs 小盘 | 沪深300 与 中证1000 的差（退而用 上证50/创业板指） |
| 量价是否互相印证 | 按成交额分成前后两组（91 个板块时各 20 只，板块少时按三分之一缩），比较两组平均涨跌；再点名成交额最大那块占两市成交多少、今天涨跌多少 |
| 赚钱效应在哪条链 | 把涨停池的 `limit_up_reason` 按关键词粗分成：半导体材料/封测/存储、算力/液冷/数据中心、机器人、新能源/电力设备、军工、医药、并购重组/国资、其他（顺序即优先级） |

字段在 `stocks_data.json` 的 `sector_cross` / 清单的 `cross` 里，`why` 记着「为什么这一轮
是横截面」（面板底部如实写出来）。看版式：

```sh
python tools/build_stocks.py --demo-cross --out preview   # 故意不给日 K 的演示
```

### RRG 的边界

- RRG 描述的是**相对**强弱的位置，不是绝对涨跌，也不是择时信号；研报的完整策略还
  包含成分股、扩散指标、月末调仓与回测，这里只复现了「象限 + 信号 A」这一层，
  **没有回测、没有收益承诺**，和面板其它段一样「仅供信息展示，不构成投资建议」。
- `today_pct` 来自快照（真实涨跌幅），RS-Ratio / RS-Mom 来自日 K 收盘价的比值；
  盘中最后一根是「未走完的日 K」，收盘后才定型。
- 参数不同、基准不同都会改变象限归属，跨面板比较前先看抬头写的是哪套参数。
- 横截面那一段是**单日快照口径**：没有时间轴就没有相对强度，它不能替代 RRG，
  只能说明「今天是怎么跌/涨的、钱在哪里」。

## 6b. 板块情绪 EW-SDM（单日横截面，策略来自 GitHub）

### 策略出处

- 仓库：[autumn-go/strategy-factor-dashboard](https://github.com/autumn-go/strategy-factor-dashboard)（「A 股策略因子平台」）
- 文件：`src/engines/ews_engine.py`，公式 `final = momentum × emotion_diff × s_score`
- 实现：`tools/ew_sdm.py`（标准库，逐条对应原版的 `calculate_emotion_weight` /
  `calculate_s_score` / `compute_daily_factors`），测试在 `tests/test_ew_sdm.py`（手算值锁定）

### 怎么读

| 量 | 含义 |
| --- | --- |
| **分** `final` | 涨跌幅 × 情绪 × 连板杠杆；正数 = 板块内资金和涨停情绪同向偏强 |
| **涨跌** `momentum` | 板块成分股涨跌幅，按（成交额 + 封单额）加权 |
| **情绪** `emotion` | 情绪权重按同样权重加权：首板 1.5、n 连板 1 + 0.5n、非涨停且涨超 3% 为 1.0，其余 0 |
| **涨停 / 最高连板** | 板块内涨停股数量与最高连板数，连板杠杆由它决定 |

分为 0 不是缺数据：板块内既没有涨停、也没有涨超 3% 的股票时，情绪为 0，原版公式就得 0。

### 数据从哪来、缺什么

面板本轮已经抓到的数据就够算：全 A 快照（涨跌幅、成交额）、涨停池（封单额、连板文本）、
同花顺行业成分股（与 A/H 龙头共用的 7 天缓存）。涨停池默认取前 100 只（`--ew-pool-size`），
因为连板杠杆要覆盖市场全部涨停；面板上的涨停表仍只显示前 `--limit-up-size` 只。

与原版的差异，面板上都会如实写出来：

1. **没有炸板/跌停数据**：原版「炸板且跌超 5% → -1.0」这条负反馈不生效，所以 emotion 恒 ≥ 0。
2. **只算单日**：原版的历史回测（净值与 RRG 对比）需要多年历史，这里不做。
3. **涨停池不全时**：池外涨停按涨幅记，连板杠杆可能偏低；面板注里会写「池 X 只，市场涨停 Y 只」。

`--no-ew-sdm` 可以关掉这一段。它独立失败：情绪段出错只会在 `errors` 里留一条，不挡指数、RRG 和港股。

### 目前的展示位置

纯文本（`stocks.txt`，RRG 之后）、EPUB 和网页仪表盘 `stocks.html` 都有强、弱各 6 个板块的表；
清单 `stocks.json` 里是完整的 91 行。

### 这次没有接入的部分

| 原版模块 | 状态 | 原因 |
| --- | --- | --- |
| BOCI 五维行业情绪 | 未接入 | F1 要成分股的 20 日均线，F3 要板块 250 日换手率，F4 要每日跌停池，F5 要 250 日板块成交额占比；现有抓取都不保存这些历史（F2 RSI 只需板块收盘，理论上可接，但单独看意义有限，暂缓） |
| 行业拥挤度 | 未接入 | 要 1250 个交易日的板块收盘与换手率；现有日 K 只有 340 根，且不含换手率 |

## 6c. 指数择时 ICU 均线 + QRS（策略来自 GitHub）

### 策略出处

- 仓库：[hugo2046/QuantsPlaybook](https://github.com/hugo2046/QuantsPlaybook)（券商金工研报复现）
- ICU 均线：`C-择时类/ICU均线/src/icu_ma.py`（`siegelslopes_ma`，窗口 5）
- QRS：`C-择时类/RSRS择时/SignalMaker/qrs.py`（`QRSCreator`，N=18、M=600、n=2、阈值 ±0.7）
- 实现：`tools/timing_quants.py`（标准库），测试在 `tests/test_timing_quants.py`

### 怎么读

| 量 | 含义 |
| --- | --- |
| **ICU** | 收盘与 5 日 Siegel 重复中位数拟合线的关系；收盘上穿为「持有」，下穿为「空仓」 |
| **QRS** | 高低价相关性的标准化斜率（RSRS）；上穿 +0.7 开仓，下穿 -0.7 平仓 |
| **穿越时点** | 最近一次穿越距今几根日 K，判断信号是新鲜的还是陈旧的 |

ICU 显示「贴线」的情况：5 点 Siegel 拟合的线会穿过某一根收盘价（大约五分之一的时候），
此时收盘与 ICU 相等，不是缺数据，文本里写成「贴线」。

### 数据从哪来

宽基指数日 K（上证指数、深证成指、沪深 300、中证 500、科创 50 等 13 个）。每轮抓 800 根
（QRS 的 M=600 外加 N，至少要 617 根），最高、最低、收盘都要。
历史按小时缓存（和 RRG 一样，在进程内存里，同一天同一批代码内复用）。注意：工作流每轮都是
新进程，内存缓存在轮与轮之间不生效，所以每轮都会重新拉这 2 个批量请求（数据很小）。

### 与原仓库的差异

1. 原仓库是 backtrader 回测，这里只算**最新一根**的状态，不做历史回测和净值。
2. ICU 与 QRS 的开平仓规则只按收盘穿越判断；原 notebook 里的滑点、佣金、印花税没有进来。
3. 指数日 K 不够（接口失败或少于 617 根）时，QRS 那一行写明原因，ICU 照常输出。

### 开关

`--no-timing` 关掉；`--timing-days` 调历史长度（默认 800）。择时段独立失败：出错只在
`errors` 里留一条，不挡指数、RRG、EW-SDM 和港股。

### 目前的展示位置

纯文本（`stocks.txt`，EW-SDM 之后，周末精简版只留 ICU 行）、网页仪表盘、EPUB 与清单
`stocks.json` 里的 `timing` 字段（完整 13 行）。
