# 字模式：把 004 排成 EPUB 交给 KOReader 阅读器

截图模式（`render_report.py`）保真，但本质是图片：放大就发虚、每轮刷新要下几 MB、
字号改不了。**字模式**换一条路——把 004 的正文清洗成 XHTML，配一套电子墨水用的
CSS，打包成单文件 EPUB。插件把它下载到设备后交给 **KOReader 自己的阅读器**打开，
于是：

- 文字是矢量渲染，任何字号都锐利；
- KOReader 已有的字号、行距、页边距、字体、进度条、字典、目录全部可用；
- 一个文件几十 KB，刷新只重下一本书，不再有几 MB 图片；
- 标题分级、表格黑线、列表缩进都是真正的排版，不是等宽字堆。

```
004 构建页  →  build_epub.py  →  site/report.epub + site/epub.json
                                        ↓ 上传到仓库
       设备：插件拉 epub.json → generated 变了才下 report.epub → 打开阅读器
```

## 1. 生成

只依赖 Python 标准库，**不需要** Playwright / Pillow：

```sh
python tools/build_epub.py https://k-macao.github.io/004/ --out site
```

输出：

```
site/report.epub     单文件 EPUB 3（含 toc.ncx，兼容旧版 crengine）
site/epub.json       {"generated", "doc", "title", "chars", "bytes", "sections",
                      "data_time", "data_time_kind", "status_removed", "source"}
```

成功时打印 `完成：84 KiB，19342 字符，site/report.epub`，并跟着打印
`状态类文字：已删除 N 块（正文全部保留）`——同一个 N 也写进清单的 `status_removed`。

手头有本地 HTML 也可以：`python tools/build_epub.py report.html --out site`
（不带 `--base-url` 时相对链接会失效）。CI 就是先把页面抓成本地的
`report-built.html`（已在 `.gitignore` 里），再让两个转换器共用这一份：

```sh
python tools/build_epub.py report-built.html --base-url https://k-macao.github.io/004/ --out site
python kindle_report.py report-built.html --format text -o kindle.txt
```

`--base-url` 用来把相对链接/图片补成绝对地址，同时作为 `epub.json` 里的 `source`
（否则清单里记的是本地临时路径，追溯不到源）。

生成内容做了什么：

- 只取 `<main>` 里的正文，`nav`/`footer`/`button`/`script`/`svg` 等整段丢弃；
- 保留 `p / h1-h6 / ul / ol / li / table / thead / tbody / tr / td / th / b / strong / em / a / img / hr` 等；
- 删掉所有 `class`、`id`、内联 `style`、`on*` 事件属性——避免 004 的样式混进来；
- `a[href]`、`img[src]` 改成绝对地址；
- 注入的 CSS：白底黑字、正文行距 1.55、标题 1.55/1.3/1.14em、表格满宽 + 1px 纯黑
  实线 + 上下 0.2em/0.3em 内边距、表头跨页重复（`thead`）、行不断页（`tr`）。

### 状态类文字不进书

正文**全部内容**都排进书里，只有「这台机器这次跑得怎么样」的话被整块删掉
（`strip_status()`，规则见 `STATUS_DROP_CLASSES` / `STATUS_DROP_IDS` /
`STATUS_CHIP_TEXT` / `STATUS_LINE_PATTERNS`）：

| 删掉 | 例子 |
| --- | --- |
| 推送框与终端状态行（按 class 整块删） | `微信推送 · 一对一专属单页完整直推`、`点击下方按钮…`、`STATUS > 一对一专属推送已就绪▌` |
| 筛选 chips（按 class 删） | `49 SOURCE FEEDS`、`全部 49 平台 / 偏多 (2) / …` |
| 逐源抓取状态与核验时间 | `抓取状态：当次未获取（robots.txt 不允许抓取）—— …`、`当次实抓 · 端点 https://… · 36 ms · …`、`未获取原因：…`、`当次抓取成功，但时效窗口内没有可核验条目`、`… · 抓取核验 2026-11-06`、`2026-11-06T11:44:52Z · … 本次匹配 3 条，展示 3 条`、行内的 `未提供站内热度指标 · …` |
| 本次构建的汇总与缺口 | `11/12 项同步成功 … · 抓取于 … · 核验日期 …`、`宏观快讯 301 条入库 · …`、`数据缺口：…`、`量化平台接口 2/11 可用 · … 9 个接口本次自动降级`、`窗口内无匹配快讯的小节：…`、`本次判定：…` |
| 构建兜底占位（产物缺失时才出现） | `◆ 宏观快讯 — 今日未获取`、`待构建注入`、`运行 python3 community_snapshot.py …`、`恢复命令：…` |
| 只剩状态标签的 chip | 社区卡右上角的 `未获取`（`中性` / `偏多` / `偏空` / `多空分歧` 是研判，保留） |

保留的边界：

- **未获取的源保留源名**——`❄️ 02. 雪球网` 这张卡只剩标题，49 源清单仍然是全的，
  删空之后的外壳容器（`div`/`p`/`li`/`article`…）顺手丢掉，不留空白块；表格单元
  不在此列，删了会让列错位；
- **口径说明与方法论注释是内容，不删**：`口径：…`、`指标口径：…`、
  `▶ 词库极性与摘录说明：…`、`注：本节结论…`、`⚠️ 风险提示`、
  `评论仅为有限样本…`、`缺口记账：3/49 个源当次未获取 —— …`；
- **时间戳行保留**：`扫描时间 … · 行情日期 … · 数据覆盖 99%`、`预测生成 … · 基准日 …`、
  `◆ 行情快照 · 11 月 6 日 · 2026-11-06 22:57:20 UTC`。源数据时间（`data_time`，
  新鲜度闸门用）本来就从这里读，而且是在过滤**之前**读的：即使以后规则更激进，
  闸门也不会拿不到时间；模板占位符检查（`{{FETCH_STATUS}}` 正好落在会被删的状态块里）
  同样跑在过滤之前。取值分三级，精度记在 `data_time_kind` 里，见 §4.6。

`kindle_report.py`（纯文本模式）带一份逐条相同的规则——它要单独拷进 004 仓库，不能
import 本仓库的模块，所以 `tests/test_status_filter.py` 会比对两边的 `STATUS_*` 常量，
并对同一批样例行断言两个转换器判断一致。纯文本没有节点边界，多两条处理：源名和状态
标签挤在一行时只切尾巴（`❄️ 02. 雪球网未获取` → `❄️ 02. 雪球网`），行内 `<span>`
抽成文字后粘在句尾时同样只切尾巴（`… 未提供站内热度指标 · 2026-11-06T11:45:19Z`）。

### 内容重排：把 004 的写作套路变成版式

004 的正文是「一句话里塞标题、标签、分数、归类、读数」，直接排版会糊成一片。脚本按它
稳定的写法做了结构识别，纯文本没有的信息层级这里补回来：

| 原文形态 | 重排后 |
| --- | --- |
| `1. 全球风险偏好（…）重点 · 利空 · 100.0 分` | `<h3>` 小标题 + 独立信号行：`重点`、`利空` 两枚描边标签 + 放大的 `100.0` |
| `归类：市场盘面　当次读数：…` | 两列 **kv 表**（左列 5.5em 固定宽加粗，右列内容） |
| `扫描时间 … · 行情日期 … · 数据覆盖 99% · 口径：…` | 同一套 kv 表（`·` 分隔的元信息也识别），`口径` 允许长文本 |
| `▶ AI 总结解读：…；提取信息：…；规则判断：…` | 左边线引用块，按 `提取信息：` / `规则判断：` 拆成独立段落 |
| `◆ 三大关注面 · …` | 四级标题 |
| 一条力量的整段（标题 + 信号 + 指标 + 证据 + AI 解读） | 收进同一张**卡片**框 |
| `结论：空头占优…　合成分 −25.1 · 置信度 100%` | 双线描边的结论框，`合成分` / `置信度` 各自成行 |
| `结论` 之外的正文长句 | 普通段落，行距 1.55 |

### 数字与方向

- 所有数字包 `<span class="num">`：**加粗**；表格里的数字单元格右对齐并整格加粗；
- 带符号的涨跌前加 **▼ / ▲**（电子墨水没有颜色，符号比红绿更可靠），并把 ASCII 减号
  统一成 `−`；
- 日期与时间不加粗：`2026-11-02`、`10:09:05`、`10 月 30 日` 保持原样，避免整页全是黑块；
- 关键分数（`重点 · 利空 · 100.0 分` 里的分数、结论框里的合成分/置信度）额外放大约 1.15–1.3 倍。

### 表格

- 004 自己的表格（02 行情快照 12 行）保留并强化：表头跨页重复、`tr` 不断页、单元格
  1px 纯黑实线；
- 数字单元格识别为 `class="num"`：右对齐 + 加粗 + ▲▼；
- `—` 这类空值不当数字处理，保持左对齐、不加粗；
- kv 表与数据表样式分离（`table.kv` / `table.data`），不会互相污染。

### 卡片：一条细分 = 一张卡

每个「细分单元」都收进一个 1px 纯黑实线框里，视觉上自成一块，翻页时尽量不拦腰截断：

| 卡片 | 框住什么 | 样式 |
| --- | --- | --- |
| `div.card`（力量条目） | 一条力量的全部内容：`h3` 标题 + 信号行 + `table.kv` + 证据列表 + `▶ AI 总结解读`，**合成一张** | 2px 黑框，`page-break-inside: avoid` |
| `div.card.slim`（要点） | 以加粗词开头的列表（如「三大关注面」）拆成一行一张小卡 | 1px 黑框，行距更紧 |
| `table.data`（行情表） | 行情快照单独成块，不被任何卡吞掉 | 表头跨页重复，1px 网格 |
| `div.verdict`（结论） | 结论框保持独立双线框，不并入力量卡 | 原有样式 |

排版规则：

- 只用 **1px / 2px 实线 + 纯黑**，不上圆角、阴影、渐变（crengine 不支持，电子墨水也糊）；
- 卡与卡之间留 `0.9em` 上边距，标题（黑底横条）不进卡，保证层级不变；
- `page-break-inside: avoid` 让整张卡优先翻到下一页；若某张卡比一屏还高，引擎会自行忽略这条规则，
  真要强制就把它在该卡上改成 `auto`（`tools/build_epub.py` 里 `div.card` 的 CSS 段）。

### 章节与目录

- 标题带**实心底色横条**，和正文硬分隔：`h2` 章节标题是黑底白字并另起一页
  （第一个章节除外，避免空白页），`h3` 力量条目是浅灰底 + 左侧 4px 黑竖条，
  `h4` 小标题是更浅的灰底；
- 每个 `<h2>` 生成锚点（`01 /` → `#s01`）；
- 书首插一页 **目录**（`toc.xhtml`），`toc.ncx` 与 `nav.xhtml` 同步指向各章，KOReader 里
  的「目录」按钮可直接跳转。

## 4. 刷新与翻页怎么走

- 每 60 秒拉一次 `epub.json`（几百字节）：
  - `generated` 没变 → **自动翻一页**（到最后一页后回到第 1 页）；
  - `generated` 变了 → 下载新 EPUB（默认上限 8 MiB），存成一个新的文件名
    `octopus004-report-<n>.epub`，然后重新打开——**新文件没有历史阅读进度，所以总是从
    第 1 页开始**，旧的自动删除。
- 刚打开的那一分钟不会翻页（留给你看首页），之后按 60 秒节奏走。
- 如果你手动打开了别的书，插件不会去翻它（只在当前文档是它自己下载的 EPUB 时才翻页）。
- 点屏幕不再有插件菜单，改用 KOReader 原生操作（左右点/滑动翻页，`Status` 之类在
  KOReader 菜单里）；插件自己的入口仍在 工具 → 004 Report。

## 4.5 自动刷新（GitHub Actions）

`.github/workflows/refresh-epub.yml` 会在仓库里定时跑一遍生成，你不用再手动执行、手动上传：

- **节奏**：cron 每 60 分钟运行一次（`0 * * * *`，每小时整点），**每次运行都生成并推送**，
  不再限流、内容没变也会提交（提交用 `--allow-empty`）。
- **做什么**：**抓一次** `https://k-macao.github.io/004/` 存成 `report-built.html` →
  跑测试 → `tools/build_epub.py`（EPUB）与 `kindle_report.py --format text`（纯文本）
  共用这一份页面 → `tools/check_no_status.py` 自检 → 提交
  `site/report.epub` / `site/epub.json` / `kindle.txt` 并推送。提交信息与目录页的
  「更新时间」是同一个时间戳。
  - 只抓一次是有意的：分别抓两次，004 正好在中间发布的话，EPUB 和纯文本就会来自
    不同的构建；两步写在同一个 step 里也是有意的——**要么两种产物一起更新，要么都不更新**，
    设备上不会出现一个新一个旧。
  - 推送用 `git push origin HEAD:refs/heads/$GITHUB_REF_NAME`：定时运行时 HEAD 就是默认分支，
    手动指定 ref 运行时是游离 HEAD，裸 `git push` 会失败。
- **自检不过就不推送**：`tools/check_no_status.py` 用生成时同一套规则逐行检查两种产物，
  发现整行状态类文字（`抓取状态：…`、`当次实抓 · 端点 …`、`STATUS > …`）就报错退出，
  这次运行不提交、不推送，设备上留着上一版；正文行数/字符数掉到下限以下同样报错
  （防过滤规则写宽了把正文删掉）。
- **源时间只警告**：生成后，job 会检查 `site/epub.json` 的 `data_time` 与
  `data_time_kind`（都来自报告正文，三级取值见 §4.6）。距今超过
  `env.MAX_SOURCE_AGE_HOURS`（默认 **12 小时**）或缺失时，只在 Actions 日志里输出
  `warning`，**仍然推送**；设备目录页同时显示源数据时间，「文件新」与「数据新」
  可以自己分辨。`kind` 必须一起传：精度只到日期时 `data_time` 里的 `00:00:00` 是
  补出来的，拿它当真实时刻算「距今几小时」，报告当天晚上就会误报过期。
  若想恢复「旧数据不推送」，需要在 job 里把这一步改回 `exit 1` 或跳过提交。
- **手动触发**：Actions → *Refresh 004 EPUB* → **Run workflow**。
- **前提**：仓库 Settings → Actions → Workflow permissions 需为
  **Read and write permissions**（否则 `git push` 会被拒）。定时任务只在默认分支上运行。
- **体积**：每次运行都是一个新提交，EPUB 约 60–100 KiB（zip 已压缩，Git 基本无法再压缩）。
  按 60 分钟一次计，一天约 24 个提交、约 1.4 MiB 历史，一年约 0.5 GiB。
  如果仓库体积是问题，可把 `cron` 改成更稀疏的间隔。

设备端无需任何改动：`generated` 一变，插件下一次 60 秒轮询就会下载新版本并从头打开。

## 4.6 数据时间：别把「文件新」当成「数据新」

`epub.json` 里有三个时间，含义完全不同：

| 字段 | 含义 | 谁产生 |
| --- | --- | --- |
| `data_time` | 报告里的**行情时间**，ISO-8601 UTC；三级取值见下 | 004 的数据源 |
| `data_time_kind` | `data_time` 的**精度**：`scan` / `build` / `date` | `build_epub.py` |
| `generated` | 这份 EPUB **文件生成**时间 | `build_epub.py` |
| 设备 `Last check` | 插件拉清单的时间 | 插件 |

- `data_time` 按三级取，`data_time_kind` 记它是哪一级：

  | kind | 取自正文哪里 | 精度 |
  | --- | --- | --- |
  | `scan` | `扫描时间 2026-11-02 10:09:05 UTC`（旧模板） | 秒 |
  | `build` | 页面构建戳 `… · 2026-11-06 22:57:20 UTC`（上游 2026-11-06 换模板后只剩这个） | 秒 |
  | `date` | `行情日期 2026-11-06` | **只到日** |

  取 `build` 时只认不晚于「现在 + 1 小时」的戳：正文里引用的未来时间（协议生效日之类）
  不能当构建时间，否则闸门永远判「很新」。同级有多个戳就取最晚的那个。
- 目录页会印一行：`更新时间：2026-11-05 18:28:00 北京时间 ｜ 源数据时间：2026-11-02 18:09:05 北京时间`。
  页面时间统一为北京时间（UTC+8）；`epub.json` 与提交信息仍为 UTC。
  第一项是本次文件生成/推送的时间（与提交信息一致），第二项是 004 报告里的源数据时间。
  `kind` 是 `date` 时改印 `源数据日期：2026-11-06`——补出来的午夜换算成北京时间是
  `08:00:00`，那是个看着精确到秒的假时刻，不能显示；
- 插件 0.4.1 起，菜单 **Status** 增加 `Data: …`；0.4.2 起 Status 中的 Data 和 Last check 都按北京时间显示（`(Beijing)`），例如 `Data: 2026-11-02 18:09:05 (Beijing)`。超过 24 小时
  会自动追加 `(stale 3d)`，一眼就能看出「新的是文件，不是行情」；
  0.4.3 起读 `data_time_kind`：`date` 时显示 `Data: 2026-11-06 (date only)`，
  年龄按当天 23:59:59 UTC 起算，不会报告当天晚上就变成 `(stale 1d)`；
- 004 的构建挂了（它自己的 Actions 在 `🧪 舆情层自检` 失败）时，`generated` 会变、
  `data_time` 不动 —— 这正是需要区分两者的场景。
- 自动刷新 job 会用 `data_time` 检查新鲜度，超过 12 小时（`env.MAX_SOURCE_AGE_HOURS`）
  只给出日志警告，仍然推送，见 §4.5。

## 5. 想调排版

不用改脚本——这些都在 KOReader 里调，插件不管：

- 字号 / 行距 / 字体：阅读界面 → 菜单 → **字体** / **行距**；
- 页边距：菜单 → **页面** → 边距；
- 主题/对比度：菜单 → **屏幕** → 夜间模式（想要白底黑字就保持关闭）。

需要**改内容风格**（比如表格线更细、标题更小）时改 `tools/build_epub.py` 里的
`STYLE_CSS` 再重新生成、上传即可。

## 6. 限制

- 单个 EPUB 上限 8 MiB（插件 `DOC_MAX`）；正文 HTML 超过 4 MiB 脚本会拒绝，
  因为老设备打开会卡。
- 抓的是**静态 HTML**：如果 004 改成前端渲染（正文由 JS 生成），`<main>` 会是空的，
  脚本会报「未找到非空的 `<main>` 报告正文」。这时改用截图模式，或让 004 侧在构建时
  把正文写进 HTML。
- 图表、图片如果依赖外链且域名不允许直连，设备上会是空白（正文和表格不受影响）。
- 阅读位置不会跨版本保留：每份新报告都是从第 1 页开始，这是刻意的。
- 回退：Display mode 随时切回 `text`（纯文本，插件自己画）或 `page images`（截图）。
